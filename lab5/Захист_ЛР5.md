# Як захищати лабораторну роботу №5

## Як відкривається сторінка результатів

Це звичайна HTML-сторінка `lab5/results.html`, додана до проєкту. IntelliJ — редактор коду; браузер показує сторінки. `START.cmd` запускає локальний HTTP-сервер Python з кореня проєкту та відкриває сторінку після готовності сервера. Якщо сервер уже працює, скрипт відкриває її одразу.

`127.0.0.1` означає цей комп’ютер, `8055` — порт сервера, `/lab5/results.html` — шлях до файлу в проєкті. Це не опублікований інтернет-сайт.

- Сторінка результатів: http://127.0.0.1:8055/lab5/results.html
- Сам портал: http://127.0.0.1:8055/index.html
- Каталог: http://127.0.0.1:8055/topics.html
- Форма: http://127.0.0.1:8055/feedback.html

У Windows натисни **Win+E**, встав у верхній адресний рядок `C:\Users\Artemka\IdeaProjects\Frontend STEM project\lab5`, натисни Enter та двічі натисни `START.cmd`. Якщо бачиш текст скрипту в IntelliJ, це лише відкриття для редагування; для простого запуску використовуй Провідник.

Числа на сторінці збережені після перевірок 19.10.2026. Перезавантаження сторінки не запускає новий Lighthouse. Кнопки «Аудит до» й «Аудит після» відкривають збережені звіти. Новий аудит запускай для сторінки порталу, каталогу або форми, а не для службової сторінки результатів.

## Що відкрити

1. У IntelliJ відкрий папку `Frontend STEM project`, а в ній `lab5`.
2. Двічі натисни `lab5/START.cmd` у Провіднику. Відкриється сторінка результатів, а за потреби запуститься локальний сервер. Вікно сервера залиш відкритим.
3. Адреса результатів: http://127.0.0.1:8055/lab5/results.html
4. Звіт для здачі: `lab5/Звіт_ЛР5_Захарченко_Варіант10.docx`.

Якщо запускати вручну, відкрий **Terminal у IntelliJ або PowerShell**, встав команди:

```powershell
Set-Location -LiteralPath 'C:\Users\Artemka\IdeaProjects\Frontend STEM project'
& 'C:\Users\Artemka\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -m http.server 8055 --bind 127.0.0.1
```

Очікуваний результат: повідомлення про сервер на порту 8055. Після цього відкрий браузер за адресою вище. Якщо порт уже зайнятий чинним сервером цього проєкту — просто відкрий адресу. Для зупинки свого сервера натисни Ctrl+C.

## Порядок демонстрації на 5–7 хвилин

### 1. Показати готові результати

На сторінці `results.html` покажи оцінки Lighthouse та посилання «Аудит до» і «Аудит після». Відкрий мобільний аудит каталогу: **54 → 99**, LCP **4,58 → 1,97 с**, CLS **0,734 → 0,010**. Головна: **83 → 98**. Форма: **83 → 98**. Настільні результати після змін: **100**.

Пояснення: «Це збережені фактичні локальні вимірювання. Кожне число можна перевірити в оригінальному HTML/JSON Lighthouse. Повторний запуск може дати трохи інші значення».

### 2. Показати адаптивність

Відкрий головну, натисни **F12**, потім **Ctrl+Shift+M**. У режимі Responsive змінюй ширину: **320**, **390**, **768**, **1024**, **1366**. Якщо потрібно, від’єднай DevTools в окреме вікно, щоб умістити ширину 1366.

Покажи: меню переноситься, кнопки доступні, сторінка не прокручується вправо. Велику таблицю прокрути **всередині її білого контейнера** — це очікувана поведінка.

На сторінці «Навчальні теми» покажи: до 520 px одна колонка, 521–1100 px дві, понад 1100 px три. У полі пошуку введи `грам` — лишиться «Граматика». Очисть поле, відкрий пункт акордеона.

Пояснення: «Я використовую RWD: один HTML-макет, відносні розміри, Grid/Flex і медіазапити. Це не окрема мобільна HTML-версія».

За потреби в Console перевір ширину:

```javascript
({ viewport: innerWidth, document: document.documentElement.scrollWidth })
```

Очікується однакова ширина документа й вікна, наприклад 390 і 390. У Console Chrome може вимагати дозволити вставлення; цей крок можна пропустити й показати готовий журнал.

### 3. Показати форму на телефоні

Натисни поле «Детально»: підказка видима, поля не виходять за межі екрана. Постав згоду, натисни «Надіслати» — з’явиться «Дякуємо!». Це навчальна фронтендна демонстрація: повідомлення на сервер не відправляється.

Пояснення: «Раніше приховування підказки зсувало прапорець під курсором. Тепер місце під підказку зарезервоване».

### 4. Показати кросбраузерність

Відкрий ті самі адреси у Chrome й Edge. У звіті покажи таблицю всіх 50 HTML-тегів і додаткових CSS/JS-можливостей.

Скажи: «Фактичні сценарії пройдено в Chrome, Edge та тестовому WebKit. WebKit не дорівнює встановленому Safari. Safari й Opera перевірено за MDN. Firefox у цьому середовищі не запустився через залежність mozglue; проходження я йому не приписую. IE не підтримує потрібний набір сучасних CSS/JS-можливостей».

Покажи в `lab5/lab5.css`: `-webkit-appearance`, `@supports not` і запасні кольори. Поясни: «Префікси вирішують конкретні відмінності властивостей; самі по собі вони не роблять сучасний JavaScript сумісним з IE».

### 5. Показати код

В IntelliJ відкрий `lab5/lab5.css`:

- `min-width: 0` — Grid-елемент може стискатися, таблиця не розтягує документ.
- `flex-wrap: wrap` — меню переноситься.
- `minmax(0, 1fr)` — гнучкі колонки без мінімальної ширини за контентом.
- `overflow-x: auto` — прокручується тільки контейнер таблиці.
- `@media` — 1/2/3 колонки, відступи та поведінка шапки.
- `max-width: 100%` — зображення не ширше контейнера.

В `topics.html` покажи `srcset`, `sizes`, `loading="lazy"` та `width/height`. В `<head>` покажи локальні шрифти й `defer`. У `lab4.js` поясни повторне використання статичних контейнерів пошуку й акордеона.

### 6. Запустити новий Lighthouse за потреби

Відкрий `index.html` або `topics.html` → **F12 → Lighthouse** (якщо вкладки немає, шукай її через `»` або меню More tools). Обери **Navigation**, **Mobile**, **Performance** і натисни **Analyze page load / Run audit**. Для порівняння повтори з **Desktop**. Назви елементів можуть відрізнятись у версії DevTools.

Для демонстрації різниці використовуй збережені аудити «до» й «після»; поточна сторінка вже виправлена. Не очікуй, що новий запуск точно повторить збережені числа. Тест виконується на localhost, тому це лабораторний результат, а не статистика відвідувачів інтернет-сайту.

## Короткі пояснення метрик

| Метрика | Що означає | Що сказати для свого проєкту |
|---|---|---|
| FCP | Перший видимий текст або інший контент | Скоротився після усунення зовнішнього @import і оптимізації ресурсів |
| LCP | Час появи найбільшого видимого елемента | У каталозі Mobile: 4,58 → 1,97 с |
| CLS | Неочікувані зміщення верстки | 0,734 → 0,010 після резервування контенту й зміни завантаження шрифтів |
| TBT | Сума блокувань понад 50 мс між FCP та інтерактивністю в аудиті | 0 мс у збережених запусках; це не INP |
| INP | Затримка відповіді на взаємодії за сеанс | Польових даних немає; не називай TBT або одну подію польовим INP |
| JS heap | Пам’ять, зайнята об’єктами JavaScript | Знімок через DevTools Protocol; не вся пам’ять Chrome |

Добрі орієнтири Core Web Vitals: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Висновки про реальних відвідувачів роблять за польовими даними на 75-му перцентилі.

Не стверджуй, що покращились абсолютно всі метрики. Наприклад, мобільний CLS форми змінився з 0,005 до 0,009; обидва значення малі. Оцінка продуктивності враховує кілька показників, тому вона може зрости попри невелике погіршення одного з них. «80 перевірок» означає комбінації сторінок, екранів і браузерів, а не 80 фізичних пристроїв.

## Відповіді на всі контрольні запитання

**1. Чи є надмірне використання стилів кроком назустріч адаптивності?**

Ні. Важливі узгоджена структура, гнучкі розміри та обґрунтовані медіазапити. Надлишкові правила ускладнюють каскад і можуть конфліктувати. У проєкті виправлення ЛР5 винесено в окремий файл lab5.css.

**2. Чи повністю забезпечує адаптивність перегляд на емуляторах?**

Ні. Емуляція допомагає перевірити ширину, орієнтацію та поведінку інтерфейсу, але не відтворює всі особливості реального пристрою: клавіатуру, сенсорне введення, системні шрифти та продуктивність. Потрібні також перевірки на реальних пристроях.

**3. Чим відрізняється адаптивність від доступності?**

Адаптивність стосується пристосування макета до екрана й умов перегляду. Доступність забезпечує можливість користування для людей з різними потребами: клавіатурну навігацію, зрозумілі підписи, контраст і роботу зі скринридером. Ці властивості доповнюють одна одну.

**4. Які проблеми виникають через відмінності браузерів?**

Відрізняються початкові стилі, вигляд полів і календарів, підтримка CSS та API, відтворення шрифтів і фокус. У цьому проєкті враховано appearance, перенесення меню, обмеження ширини Grid-елементів та резервні кольори для color-mix().

**5. Яка основна причина відмінностей між браузерами?**

Браузери використовують різні рушії та версії реалізації вебстандартів. Chromium застосовує Blink, Firefox — Gecko, Safari — WebKit. Окремо впливають операційна система, системні елементи форми та встановлені шрифти.

**6. Яка роль HTML5 у кросбраузерності?**

Стандартна семантична розмітка робить структуру документа зрозумілою для сучасних браузерів і допоміжних технологій. Теги header, nav, main, section, article і footer описують призначення блоків. Водночас HTML5 не гарантує однакового вигляду без CSS і перевірок.

**7. Як досягти кросбраузерності правилами CSS?**

Використовувати підтримувані властивості, перевіряти довідник сумісності, задавати резервні значення й застосовувати @supports. Вендорні префікси додавати там, де вони потрібні за даними сумісності. У проєкті є -webkit-appearance та резервна палітра нічного режиму.

**8. Які фреймворки спрощують кросбраузерний фронтенд?**

Bootstrap і Foundation надають адаптивні компоненти та сітки. Tailwind CSS допомагає узгоджено задавати стилі та брейкпоінти. Autoprefixer додає префікси під обрані браузери. Жоден інструмент не замінює перевірку конкретної реалізації.

**9. Які основні класи метрик ефективності?**

Метрики продуктивності: FCP, LCP, INP, CLS, TBT, обсяг ресурсів, час JS і пам’ять. Метрики коду: LOC, складність, дефектність, зв’язність. Метрики UX і бізнесу: конверсія, залученість, відмови, CSAT і NPS. Для останніх потрібні дані реальних користувачів.

**10. Як запобігати поганим метричним показникам?**

Зменшувати зображення й кількість мережевих залежностей, використовувати srcset і lazy loading, резервувати місце для контенту, завантажувати скрипти через defer та уникати довгих завдань. Після змін повторювати вимірювання в однаковому профілі й аналізувати причини, а не лише оцінку.

**11. Які інструменти вимірюють ефективність фронтенду?**

Lighthouse і Chrome DevTools підходять для локального аудиту. PageSpeed Insights поєднує лабораторні та доступні польові дані публічних сторінок. WebPageTest виконує синтетичні перевірки. Sentry, New Relic і Datadog допомагають спостерігати за помилками та досвідом користувачів.

**12. Як фреймворки й бібліотеки впливають на метрики?**

Вони можуть покращити організацію коду, розділення завантаження й повторне використання компонентів. Водночас зайві залежності збільшують обсяг JavaScript і витрати CPU. Для невеликого статичного Learn + earn достатньо HTML, CSS та JavaScript без додаткового UI-фреймворку.
